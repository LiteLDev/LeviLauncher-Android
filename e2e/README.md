# End-to-end launch test

`run_e2e.py` drives the real launcher on a device or emulator from pressing **Launch** to a
running game, using a placeholder game package instead of Minecraft. Everything on the launcher
side runs for real: version detection, the Play Store and login gates, extraction and native image
preparation of the game libraries, the preloader, inbuilt mods, `MinecraftActivity` and the stub
`com.mojang.minecraftpe` classes.

```bash
python e2e/run_e2e.py                       # game 1.26.60.5
python e2e/run_e2e.py --version 1.26.70.1   # any version; selects the launcher's launch path
```

Each run writes logcat (filtered and full), screenshots and the Gradle log to `e2e/out/<time>-<version>/`.

## What the placeholder game is

`placeholder-game` is an app module (only included with `-Plevi.e2e=true`) that installs as
`com.mojang.minecraftpe` with the chosen `versionName` and implements the game-side contract the
launcher relies on:

| Game part | Placeholder |
|---|---|
| `libminecraftpe.so` | GameActivity glue from the same `games-activity` version the launcher ships, so `GameActivity.initializeNativeCode` resolves from it like from the real game; `android_main` renders frames with EGL/GLES2, handles lifecycle commands and input. |
| Game JNI natives (`com.mojang.minecraftpe`, XAL, Xbox, FMOD) | Every `native` method declared in the `minecraft` module, generated by `tools/gen_jni.py`; each call is logged and returns a fixed default (`false`, `0`, `""` or `null`). Stateful ones (resize, suspend/stop/destroy/shutdown, key handler, text box, network, headphones, device id, publish build) are hand-written in `game.cpp`. The build fails if the generated file is out of date. |
| Startup calls into Java | The game calls the stub `MainActivity` getters the real game uses at startup (`getAndroidVersion`, `getScreenWidth`, `getExternalStoragePath`, ...) from its own thread; a missing method or exception fails the run. |
| `libHttpClient.Android.so` | The real library, built from the launcher's own source tree (the launcher's PlayFab links against it). |
| `libc++_shared.so` | The NDK's. |
| `libfmod.so`, `libMediaDecoders_Android.so`, `libMallocRedirect.so` (from 1.26.70) | Report that they were loaded; `libfmod.so` also has the `org.fmod` natives. |

All placeholder output is logged under the `LeviPlaceholder` tag.

## What a run checks

1. Every `MinecraftLaunchTrace` milestone, in order, with no launch failure.
2. The launcher loaded each game library, and `libminecraftpe.so` is the requested version.
3. `android_main` started, all startup probes passed, an EGL surface exists, the game resumed and frames keep advancing with `MinecraftActivity` in front.
4. A key event and a touch reach the game.
5. Home then back: the game pauses (`nativeSuspend`, `PAUSE`, `STOP`), resumes and renders again.
6. The game stays healthy for `--soak` seconds: no fatal exception, native crash or crash-buffer entry.

## Local setup

- **Device**: one that can run arm64-v8a code. An x86_64 emulator image with ARM translation
  (Android 11+) works; the launcher itself only ships arm64-v8a.
- **Play Store check**: add `dev.skip_play_store_check=true` to `local.properties`. Only debug
  builds read it; CI never sets it, so published APKs keep the check.
- **Discord SDK library**: the launcher's prebuilt `libgxcore.so` links against
  `libdiscord_partner_sdk.so`, so `app/libs/discord_partner_sdk.aar` must contain
  `jni/arm64-v8a/libdiscord_partner_sdk.so`. CI downloads the real AAR with a token; without access,
  take the library from a CI-built debug APK of the same commit
  (`gh run download <run id> -n LeviLauncher-debug-apk`) and add it to the local AAR.
- **Launcher-managed login** must be off (the default), as the placeholder has no account.
- The runner never replaces a real Minecraft install: if `com.mojang.minecraftpe` on the device is
  not the placeholder, it stops and asks you to uninstall it.

## Limits

- `libgxcore.so` is a closed prebuilt. The run proves it accepts the placeholder libraries on the
  tested launch paths, not what it checks in a real game.
- The placeholder's libraries contain none of the game's code, so preloader signature hooks and
  inbuilt mods find nothing to hook (the launcher logs this and carries on, as designed).
